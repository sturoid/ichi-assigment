Python 3.12, standard library only. Code is in `src/services/htmlParser/`, tests in `tests/services/htmlParser/`.

**Run the tests:**

```
cd tests/services/htmlParser && python -m unittest
```

**Parse a file:**

```
cd src && python -m services.htmlParser <file> --as matrix|records|kv|grid [--spec ibc2018-504.3] [--no-grid] -o out.json
```

**Decisions made while building phase 1:**

- Code tables use an explicit `MatrixSpec`, for example `specs.py: IBC2018_TABLE_504_3`, rather than auto-detection. These tables are law and there are only a few of them.
  - The parser checks the HTML against the spec.
  - Duplicate keys, missing labels and non-numeric values each raise an error or a warning.
  - A header-depth heuristic cross-checks the spec's stub-column count.
- `lookup()` matches exactly, ignoring only case and spacing. Mapping `R-3` to `R`, or `NFPA 13D` to `S13D`, is a separate resolver (phase 3 or 4), so the table never guesses.
- The expected values in `tests/fixtures/expected/table-504.3.expected.json` were transcribed by hand from the printed table, not generated from parser output. They are pending your spot-check.
- Parsed outputs in `tests/fixtures/parsed/*.json` are generated by the CLI and are not test inputs. Regenerate them after any parser change.
  - In the output, `cells[]` and `index` are what a lookup caller reads; `render_sentence()` gives a one-line reading on demand. Code tables are queried through `services/codeStore`, not through these files.
  - `--no-grid` shrinks the file.
- **Header detection is structural.** The rules are in the `headers.py` docstring.
  - **Where a header starts:** at a `<th>` or bold row, or at a row that has merged cells and no numbers or dimensions in it.
  - **How far it extends:** through every row covered by a header rowspan, then through the child row under any column-group cell, then through any rows made entirely of `<th>`.
  - **What is recorded:** `layout.method` notes which signals fired.
  - **Tie-breaker (scenario P15):** a plain column whose label is already in the header, and not merged down, can't have a child label under it. A row with text there is read as data, and `review_items` records the alternative and the override (`header_rows=N`). An all-`<th>` row overrides the tie-breaker (guard P17). This was the user's decision: treat as data, record for review.
  - **Repeated headers:** body rows that reprint the header block exactly are dropped, listed in `layout.repeated_header_rows`, and warned. The match is exact, so a reprint with an OCR typo stays a data row.
- **`warnings` vs `review_items`:** warnings are parser-quality notes. Review items are choices between two readings; the chosen one is used and the other is recorded. Each is a dict with `code`, `rows`, `cols`, `chosen`, `alternative`, `override` and `message`. Dropping rows is always a review item, and the dropped text is kept.
- **Key/value sheets** record their `mode`: `label_value` (2 columns), `paired` (label/value/label/value, always with a review item), or `inline_colon` (`LABEL: VALUE` in one column).
- **Inside cells,** `<br>`, `<p>`, `<div>` and `<li>` are line breaks, so both readings of a split word are kept. Nested tables are flattened into the cell with spaces between their cells, and warned.
  - **Flat unstyled headers:** a header with no merged cells is still reported, not guessed.
- **Structure scenarios** live in `tests/fixtures/scenarios/`. See the README there for the catalogue of shapes the parser is proven against, and the open gaps grouped by fix.

Original design notes follow.
Built from two independent passes over the fixtures, one by Opus and one by Sonnet. Both resolved the same Table 504.3 cells, and those cells were then checked against `instructions/readme_images/table-504-3.png`.

## Goal

Turn OCR'd or scraped HTML tables into JSON that code and LLMs can look up **by name, not by position**.

- **Code tables** (for example IBC 504.3) are the law. The parser has to resolve every cell exactly.
- **Project tables** (code analysis, window schedule) are the submitted claims. They are noisy, so the parser keeps the raw text and records every repair it makes.

The parser must not be built around these three files. Other projects will have different columns, column orders and OCR errors.

## Architecture: three layers

```
HTML ──► [1] Grid resolver ──► Grid JSON (lossless, generic)
                                  │
                                  ▼
         [2] Header/stub detection ──► header paths per column, stub columns per row
                                  │
                                  ▼
         [3] Projections ──► MatrixTable | RecordTable | KeyValueSheet  (JSON)
```

### 1. Grid resolver (generic, knows nothing about buildings)

- Follows the HTML table-placement algorithm: each cell goes into the next free slot, and rowspan/colspan claim slots below and to the right.
- `colspan=""` and `rowspan=""` (which appear on almost every cell in 504.3) count as 1. Values that are missing, zero or not numbers also count as 1.
- Every slot records:
  - `origin: {r, c}`
  - `inherited: true|false` (true when the value was filled in from a span)
  - `raw` (the text exactly as in the source)
  - `text` (whitespace collapsed)
  - `footnotes`, pulled out of `<sup>`. For example, `NS<sup>c, d</sup>` gives `text: "NS"` and `footnotes: ["c","d"]`, never `"NSc, d"`.
  - `marks` (for example the `changed_ICC` span class)
  - `tag` (td or th)
- A text break in the middle of a word is kept as candidates rather than resolved here. `"SCREE\n N"` gives `join_candidates: ["SCREE N", "SCREEN"]`, and layer 3 picks one against a vocabulary.
- Asserts:
  - After resolution, every row is exactly the grid width.
  - No two spans overlap.
  - No span runs past the end of the table. If one does, it is flagged and cut off rather than crashing.

### 2. Header and stub detection (generic heuristics, overridable)

- The `<th>` tag is never trusted. In the window schedule, header row 2 uses `<td>`.
- **Header rows**: the rows above the first row that looks like data. A data row is mostly numbers, dimensions or short codes, or comes after a separator row.
- **Header path per column**: a structured list, never a joined string.
  - Empty parents are dropped, so `["", "SCREEN"]` becomes `["SCREEN"]`.
- **Stub columns**: the leading columns whose cells act as row labels.
  - In 504.3 these are cols 0 and 1. The sprinkler column is labelled "SEE FOOTNOTES", and "TYPE OF CONSTRUCTION" has colspan 10 and also spans over it.
- **Separator rows** (all cells empty, or a single full-width empty cell) are dropped.
- Duplicate header paths (`TYPE`, `TYPE`) keep separate column ids such as `c4` and `c5`. They are never merged.

### 3. Projections (one per table kind)

**a) MatrixTable** is for code tables. Every data cell becomes one self-describing record, so lookup is a key match:

```json
{
  "table_id": "IBC2018-T504.3",
  "title": "Allowable Building Height in Feet Above Grade Plane",
  "unit": "ft",
  "dimensions": {
    "occupancy":    {"values": ["A","B","E","F","M","S","U","H-1","H-2","H-3","H-5","H-4","I-1 Condition 1","I-3","I-1 Condition 2","I-2","I-4","R"]},
    "sprinkler":    {"values": ["NS","S","S13R","S13D"]},
    "construction": {"values": ["I-A","I-B","II-A","II-B","III-A","III-B","IV-HT","V-A","V-B"]}
  },
  "cells": [
    {
      "key": "R|S13D|V-B",
      "occupancy_row_label": "R",
      "occupancy": ["R"],
      "sprinkler": "S13D",
      "construction": "V-B",
      "value": 40,
      "value_kind": "number",
      "footnotes": ["h"],
      "sentence": "Table 504.3: occupancy R, sprinkler S13D, construction V-B → 40 ft",
      "src": {"grid_row": 16, "grid_col": 10, "raw": "40", "inherited": false, "origin": {"r": 16, "c": 10}}
    }
  ],
  "index": {"R|S13D|V-B": 0},
  "legend": {"UL": "Unlimited", "S13D": "NFPA 13D / IBC 903.3.1.3"},
  "footnotes": {"d": "The NS value is only for use in evaluation of existing building height…"},
  "grid": "<the full layer-1 grid, kept so the table can be re-projected without re-parsing>"
}
```

Lookup rules:

- `UL` is stored as `value: null` with `value_kind: "unlimited"`. It is never coerced to a number.
- A row label that lists several groups (`"A, B, E, F, M, S, U"`) is split into one cell per group, so each group can be looked up directly.
- Mapping a project's occupancy text to a table row happens in a small resolver, not in the parser:
  - `R-3` maps to `R`.
  - `H-2` has its own entry.
  - `I-1` with no condition is ambiguous, and returns an "ambiguous" result rather than a guess.
- Construction aliases: `IV`, `IV-HT` and `IV HT` all map to `IV-HT`. `VB`, `V B` and `Type V-B` all map to `V-B`.
- Footnotes are merged from the row label, the sub-row label and the cell, so a lookup returns every caveat that applies. For example, R/NS carries `d` and `h`.
- Legend and footnotes come from the companion `.md`, which the scrape dropped.

**b) RecordTable** is for schedules. There is one record per row, with cells keyed by column id:

```json
{
  "columns": [
    {"id": "c4", "header_path": ["TYPE"], "role": "operation"},
    {"id": "c5", "header_path": ["TYPE"], "role": "type_mark"},
    {"id": "c2", "header_path": ["NOMINAL SIZE", "WIDTH"], "role": "nominal_width"}
  ],
  "rows": [
    {
      "src_row": 6,
      "cells": {
        "c2": {"raw": "3' - O\"", "norm": "3'-0\"", "parsed": {"inches": 36},
               "repairs": [{"rule": "letter-O→0 in dimension", "confidence": "high"}]}
      }
    }
  ]
}
```

- Column roles are assigned by header vocabulary first and by content second. Position is never used.
  - Example: the TYPE column whose values look like `CASM'T`, `FIXED`, `S.H.` is `operation`. The TYPE column whose values are single letters is `type_mark`.
- Every role assignment records its reason and confidence.

**c) KeyValueSheet** is for the code analysis.

- A title row with colspan equal to the full width becomes the sheet title.
- Labels are matched to canonical keys through a vocabulary with a fuzzy fallback. That fallback is what fixes `FIRE SPRINKLE RS` and `GRADE PLAN E`.
- Values keep the raw text and a parsed form:
  - `41' - 6" (TO AVG…)` parses to `{inches: 498, note: "TO AVG. HT. OF HIGHEST ROOF SURFACE"}`.
  - `YES … NFPA 13D (IBC 903.3.1.3)` parses to `{sprinkler_system: "S13D", evidence: ["NFPA 13D", "903.3.1.3"]}`. If the two indicators disagree, the conflict is flagged.

### Shared value parsers

- Feet and inches: handles `2' - 6"`, `2'-6"`, `2'6"`, `30"`, `2'`, and the OCR letter `O` in a digit slot.
- Y/blank flags.
- Footnote lists.
- `UL`.

Every repair is logged. A repair is only applied where the slot is expected to hold a number, never in labels.

## Output format and storage

- One JSON file per parsed table, for example `data/parsed/table-504.3.json`. The file holds:
  - `schema_version`
  - `source_file`
  - `source_sha256`
  - `parsed_at`
  - the projection, and the grid.
- JSON is chosen because it is diffable and human-checkable, needs no database for this scale, and loads directly into code or an LLM prompt.
- For LLMs, a `sentence` field on each cell and a `lookup(occupancy, sprinkler, construction)` function together mean the model never reads table geometry. It calls the lookup or reads the matching sentence.
